# 给 AI 编程助手：根据用户的使用记录调优 NB 输入法

这份文件是写给 agent（Claude Code、Codex、Cursor……）看的。用户在菜单栏点了「和 Agent 一起调优…」，把一段提示词粘给了你，里面有源码和本机数据的路径。你的活：从用户最近的真实使用里找出**反复出现**的错，跟用户商量着改好，改完记一笔，下次接着来。

先记住四件事：

- **数据是用户说过的每一句话，只在本机读。** 别贴到网上、issue、PR 描述里；举例时引用一两句够说明问题就行。
- **先给用户看，同意了再改。** 热词、提示词、代码都一样。用户想要的是「和你一起打磨」，不是回来发现东西被改了。
- **同一个错至少出现两次才动手。** 只出现一次的记在调优记录里，下次再看。
- **能自己验证的自己验证。** 下面写了怎么用录音重放识别、怎么批量跑润色。

## 第一步：看上次调到哪

读调优记录 `tuning.md`（路径在提示词里，可能还不存在）。每一节以 `## 日期` 开头，记着当时看了什么、改了什么、留着没改的。这次只看那个日期以后的数据，上次「留着观察」的问题这次重点看有没有再出现。

## 第二步：找问题

### 改字记录（最有用）

`edits/edits.jsonl` 一行一次输入：

| 字段 | 意思 |
|---|---|
| `recognized` | 识别出来的字（已经过一定替换、热词读音纠正） |
| `typed` | 润色后真正输进去的字 |
| `final` | 用户在输入框里改完的样子（输入后盯 1 分钟左右，换了焦点就停） |
| `changed` | 用户有没有改 |
| `audio` | 录音文件名；改过的那段另存在 `edits/` 目录里 |
| `app` | 输进了哪个应用 |

只看 `changed: true` 的，按错在哪一步分：

- **识别错**：`recognized` 里就错了，`final` 改对了（「A 帧」→「Agent」、「日色」→「润色」）。→ 热词或一定替换，或者识别后处理的代码。
- **润色错**：`recognized` 是对的，`typed` 被改坏了（删了有用的话、改了字），用户又改回去。→ 润色的提示词或检查。
- **标点、格式**：只差标点、空格、换行。看是不是一类问题（短句没句号、两句粘在一起）。
- **不是错**：用户只是改主意，接着往下写，或者删掉重说。这类不管。`final` 比 `typed` 长很多、多出来的是新内容的，多半是接着写。

`final` 里可能带着输入框里前后的别的字，比对时找 `typed` 对应的那一段。

### 日志

`~/Library/Logs/NBIME.log` 一行一件事。值得 grep 的：

| 关键字 | 说明 |
|---|---|
| `预览` / `结果` | 说话时的预览和最终结果。**预览对、结果错**多半是服务端后处理（比如数字转换），不是听错 |
| `按规则替换` / `按读音换回热词` / `正负号换回字` | 识别后处理生效了 |
| `像是抄了热词表` / `前面抄了` / `复核` | 人声太弱时识别模型会把热词表原样抄出来。热词越多越容易抄 |
| `润色 … 用原文` | 模型的结果没过检查，后面写着原因（删了人称、删得太多、丢了热词……） |
| `松开后 NNNms` | 速度。经常超过 1500ms 要看是识别慢还是润色慢 |
| `焦点不在输入框` / `可能没输进去` | 粘贴落空 |
| `按下没反应` / `先收掉` | 快捷键问题 |
| `没声音` / `音量峰值` | 收音问题 |

### 热词和设置

- `hotwords.txt`：一行一个热词；有等号的是「一定替换」规则（`错的、另一种错法=对的`，左边至少两个字）。
- `config.json`：`polishClean`、`polishFormat` 是润色的两档（off / mid / strong）。看问题前先确认用户开着哪档，关着的那档出的「问题」可能是故意不改。

## 第三步：怎么改（按这个顺序考虑）

1. **热词**（最轻，用户自己也能在「设置 › 热词」里看到、撤销）
   - 专有名词识别不出来：加成热词。
   - 总是错成同一个样子、加热词也压不住：加一定替换 `错的=对的`。先在录音上试热词压不压得住（第四步），压不住再加规则。
   - 左边会不会误伤：搜一遍改字记录和日志，看左边那几个字有没有在别的正常句子里出现过。
   - 热词别越加越多，抄热词表的风险会变大；用不上的可以建议删掉。
2. **识别后处理的代码**（`client-mac/Sources/`）：`Replace.swift`（一定替换）、`Hotfix.swift`（按读音换回热词）、`Signfix.swift`（服务端数字转换的误伤）。一类有规律的错，用代码修比一条条加规则好。
3. **润色**（`Polish.swift`）：提示词、例子和检查。经验：小模型的提示词改一处常常别处变坏，**能用代码检查拦住的，优先在检查里拦**（`problem(raw:out:...)`，拦下来就用原文）。改提示词前后都要跑第四步的润色测试对比。
4. **服务端**（识别服务、润色模型所在的机器）：不要直接改，把发现和建议写给用户，让用户决定。

改代码以后 `cd client-mac && ./build.sh` 编译、装好、重启 app。

## 第四步：验证

app 要开着（测试借它的连接）。`NBIME` 是 `~/Applications/NB 输入法.app/Contents/MacOS/NBIME`。

- **重放录音**：`NBIME --test-file <录音.wav>`，打印预览和最终结果（`RESULT …`），走完整流程（热词、替换、润色）。录音会随机采样，同一段至少跑 3 次。改过字的录音都在 `edits/` 里，正好拿来当评测集。
- **只测润色**：把句子一行一句写进文件，`NBIME --polish-test <文件> --levels 中中,强中,中强,强强`，一行一个 JSON（`raw`、`out`、`note`、`sec`）。`note` 里能看到没过检查的原因。刚重启 app 的头几秒连接还没起来，结果会全是原文、`sec` 是 0，等几秒再跑。
- 改了热词不用重启，下一次识别就读新的。

## 第五步：给用户看，再改

一次把发现列给用户，每条写：

- 什么错，出现了几次，举一两条证据（时间、原来的字 → 用户改成的字）；
- 错在哪一步（识别 / 润色 / 粘贴……）；
- 打算怎么改，验证结果（改前改后各几次对）；
- 有没有副作用。

用户同意的改，不同意的不改。热词直接改 `hotwords.txt`，格式保持不变。代码改动等用户说提交再提交。

## 第六步：记一笔

在 `tuning.md` 末尾加一节（文件不存在就新建，第一行写 `# NB 输入法调优记录`）：

```markdown
## 2026-11-01

看了 10-28 以后的 312 次输入，改过 27 次。

- 改了：热词加一定替换「A帧、A 帧=Agent」（3 次）；润色检查加「删了『更正』就用原文」（2 次）。
- 没改：「下周一下周二」被删成「下周二」，用户说可以接受。
- 留着观察：「清凉」听成「轻量」出现 1 次。
```

日期写今天，`##` 后面紧跟日期，菜单里「又攒了几处改字」就是从这个日期往后数的。最后跟用户说一句这次改了几处、下次大概什么时候再来（比如又攒了二三十处改字时）。
