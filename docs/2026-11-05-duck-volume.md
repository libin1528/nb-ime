# 说话时压低正在播放的声音

2026-11-05。用户用 QQ 音乐和外置耳机实测后决定：不暂停播放器，改为说话时平滑压低系统音量，结束后渐进恢复。开关在「设置 › 通用 › 声音」，默认关。沿用 `config.json` 的 `pauseMedia` 键及对应字段，之前打开的开关不会丢；这个历史键现在只表示压低音量。版本保持 0.2.4（build 6）。

## 为什么放弃暂停

先前试过 MediaRemote 的显式 pause／play：自建媒体会话能收到命令，播放器也确实可能停下来。但第三方读取 now-playing 已受系统限制：本机 macOS 26.6.2／Darwin 25.6 上，读取状态得到 false、PID 得 0、info 得 nil；`mediaremoted` 日志对探针返回 `Operation not permitted`，不能把这些空值当作可靠状态。

随后试过用 CoreAudio 验证 pause 是否生效。设备级 `kAudioDevicePropertyDeviceIsRunningSomewhere` 会被其它 I/O 和输入流长期保持为真，所以改成按进程看 `IsRunningOutput`。自建会话暂停后能停止输出，但这不代表所有真实播放器都这样做。

**QQ 音乐的实际反例**：用户日志显示发 pause 后音乐确实停播，但 QQ 音乐的进程 `IsRunningOutput` 仍为真。程序判成“未暂停”、压低音量，并且没有记下恢复媒体的责任，结束后没有 play，音乐就一直停着。运行标记只能说明音频引擎／输出流仍在工作，不能确认播放器是否暂停；读取 now-playing 又被拒绝，无法可靠判断“是不是我们暂停的”。

因此整条暂停路线移除：产品和测试不再包含 MediaRemote 动态加载、pause／play、停止输出验证或恢复播放器；之前放在 build 下的相关临时控制探针也已清理。以后不向任何播放器发命令，不尝试重启已暂停的音乐。**播放进度始终继续。**

## 实测后的响应时间调整

用户在 QQ 音乐、外置耳机上测到旧音量方案仍然太慢：

| 时间 | 事件 | 距按下 |
|---|---|---|
| 10:03:23.216 | 热键按下 | 0 |
| 10:03:23.661 | 等开麦、holdThreshold 后才安排下降 | 445ms |
| 随后 | 再等开始提示音 0.56 秒，才执行 0.25 秒下降 | 继续等待 |
| 10:03:24.483 | 降到 0 | 1267ms，约 1.3 秒 |

因此用户改为“按下就降，不要开始提示音”：取消提示音优先及其时长等待，把下降缩短到 0.15 秒。仅提前调用仍不够，主线程开麦时可能阻塞原来的主线程定时器，所以检测与曲线都移到专用串行队列。

## 最后的做法

进入 `holding` 的同一时刻立即调用 `MediaDuck.begin`，先于开麦、取焦点以及上一句的粘贴／改字收尾。这个调用只提交后台任务，不同步读设备或等待工作队列；随后照常开麦。

- 有外部输出：后台完成检测就用 `3t² − 2t³` 平滑曲线，在 0.15 秒内从当前音量降到 0。本次接管压低后跳过开始提示音，不等 `holdThreshold`，不等开麦或提示音。
- 没有外部输出、设备已静音、原音量为 0，或设置未开启：不接管、不写音量，开始提示音仍在原来的长按确认时机播放。两种活动检测都失败时也不猜测。
- 专用队列的 `DispatchSourceTimer` 每 10ms 推进曲线，不依赖主线程 run loop。按下总耗时为检测／排队耗时加约 150～160ms；正常热路径预计约 0.15～0.20 秒，不是系统实时性保证。
- 只在每次开始时检测外部输出，没有等待播放器停止的轮询；曲线之外的周期检查用于识别用户调节和设备切换。
- 主音量可写时用主音量；否则逐声道控制并保留左右比例。声道写入部分失败时回滚已写的声道。
- 连续录音保留最初的原音量，从当前值平滑接续，不把 0 或中间值当原值。若下一句前外部输出已消失，只归还旧音量，不再压低。
- 用户或其它应用改了音量，就停止自动覆盖，结束提示音和退出时也尊重新值；自己的写入采用设备回读值，兼容量化步长。
- holding 阶段松开、取消或开麦失败，立即提交 1.25 秒恢复，不放提示音；这一步在停止麦克风之前提交，停止开麦设备也不会拖住恢复。
- 普通松开时，仍先抬到至少原音量 30%，回主线程立即播结束提示音，并从该音量用 1.25 秒继续上升。当前高于 30% 就保持；未开提示音则直接渐进恢复，不做抬升。
- tail 的重复结束不会取消或重新计时；每次按下都有请求编号，已松开或被下一次替代的检测不能迟到地压低音量，旧提示音回调也不会串到下一句。
- 退出会等专用队列归还原音量后再继续，不留下排队的写入；设备切换只归还旧设备。读写错误尝试归还，未成功的归还在退出时重试。

`Sounds.start` 已恢复原来的无返回值写法，不再读取提示音时长；`waitForStartSound` 及等待开始提示音的状态全部删除。没压音量时的开始提示音只做异步的本次接管判定，不会抬音量或重新安排下降。

`Recorder` 的中断处理和原有 tail 判断保持原样。进入 holding 提前后，开麦失败会显式回到 idle。日志使用“压低音量／恢复音量”前缀，新增后台检测耗时和“按下至降到 0”的毫秒值；日志写入与日期格式化加锁，避免与主线程日志并发冲突。

## 保留的进程检测与本机例外

通过 `kAudioHardwarePropertyProcessObjectList`、`kAudioProcessPropertyIsRunningOutput`、PID 和 BundleID 找外部输出。不用设备总体运行标记当首要判断，只有输入的麦克风进程不算。排除自身 PID／自身 bundle id，保留现有精确排除项 `com.newbaselab.clawchattest`。

先前在默认外置耳机上读取 36／37 个音频进程，属性均成功，没有权限申请。唯一持续报告输出的是该 ClawChat 测试宿主；旧 NBIME 曾是 `Input=1、Output=0`，提示音又会短暂输出。`audiomxd`、`mediaremoted` 等系统进程未见持续输出，没有对系统进程或 bundle 前缀做宽泛排除。

这一个测试宿主排除项按用户要求保留，**它真正播放语音／通话时也会被忽略**；无法仅凭运行标记判断它是否输出全零采样。正常 `com.newbaselab.clawchat` 不在排除名单。日志按变化列出实际 bundle id、PID 和被排除项。

进程列表或相关属性读取失败时，保留原有的设备级活动检测兜底并记录属性名、OSStatus；设备也不可读则不接管。设备级兜底仍可能把持续 I/O 当成播放，这是读取失败时的有限降级。

- 并发检查：故意阻塞主线程，后台仍须下降和恢复；用信号量卡住外部输出检测，验证 `begin`／短按 `end` 立即返回，松开后迟到的检测不写音量，快速连按只处理最新一次。测试设备、时钟和日志使用锁；测试不写系统音量或用户日志。
- 默认外置耳机上的只读探针：采用真实 CoreAudio 设备与进程检测，音量 setter 隔离为内存，并模拟主线程开麦阻塞 400ms。后台检测 **7ms**，按下到内存音量降到 0 **159ms**，开始提示音被跳过，内存音量恢复，真实系统音量不变。空闲时仅用 `afplay -v 0.02` 短播系统 Glass 声音作检测源，没有控制 QQ 音乐或其它用户播放器。

## 已知限制

- 进程有输出不等于采样有声音，尚未登记的空流仍可能触发压低；这次只用它决定是否压音量，不再拿它证明播放器暂停。
- 进程检测是全局的，实际音量控制仍只针对默认输出设备。应用另选的设备、接收器硬件音量，以及没有可写音量的 HDMI／数字／虚拟输出不保证受控。
- 强制结束、崩溃、设备拔掉而无法写入时，不能保证立即归还；正常退出和可处理的错误有恢复出口。
